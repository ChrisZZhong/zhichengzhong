## What happens when you type a URL in a browser?

<span id="what-happend-when-you-type-a-url-in-browser"></span>

1. The browser parses the URL to identify the scheme, host, port, and path. A fresh cached response can satisfy some requests immediately.
2. To reach the origin by name, the browser looks up the host. The browser, operating system, or DNS resolver can reuse a cached DNS answer. DNS resolves names to records, including IP addresses. The HTTP cache stores responses.
3. The browser reuses a suitable connection or opens one. A typical HTTPS request over HTTP/1.1 or HTTP/2 establishes TCP and then negotiates TLS. HTTP/3 uses QUIC over UDP.
4. The browser sends an HTTP request. The server or an intermediary returns a status, headers, and usually a body.
5. The browser parses the response and may fetch styles, scripts, images, or other resources before rendering the page.

## OSI vs TCP/IP

The OSI model describes seven conceptual layers. The TCP/IP model groups the protocols used on the Internet into four layers.

| TCP/IP layer | What it does | Examples |
| --- | --- | --- |
| Application | Defines the messages exchanged by applications | HTTP, DNS, SMTP, SSH |
| Transport | Carries data between application endpoints | TCP, UDP |
| Internet | Addresses and routes packets between networks | IPv4, IPv6 |
| Network access | Moves frames across the local link | Ethernet, Wi-Fi |

ARP resolves local IPv4 addresses to link-layer addresses. NAT translates addresses and, in common deployments, port numbers as packets cross a network boundary.

### TCP vs UDP

TCP provides an ordered byte stream with retransmission, flow control, and congestion control. UDP sends independent datagrams with no built-in delivery or ordering guarantee. A protocol on top of UDP can implement those guarantees when it needs them.

### TCP three-way handshake

The client sends SYN, the server returns SYN-ACK, and the client acknowledges with ACK. This establishes the connection and synchronizes each side's initial sequence number.

### TCP four-way handshake

A normal close ends each direction independently. One endpoint sends FIN, and its peer acknowledges it. When the peer also finishes sending, it sends its own FIN and receives an ACK. FIN and ACK can sometimes be combined. The side in TIME-WAIT can still acknowledge a retransmitted FIN and allows old packets to expire.

## HTTP

HTTP defines requests, responses, and their semantics. Each request carries the context needed to interpret it. Servers can still associate requests with a session through mechanisms such as cookies.

### HTTP request

An HTTP/1.1 request starts with a method, request target, and version. It includes headers and can contain a body.

```http
GET /index.html HTTP/1.1
Host: www.example.com
Accept: text/html
```

### HTTP response

An HTTP/1.1 response starts with a status line, followed by headers and, where applicable, a body.

```http
HTTP/1.1 200 OK
Content-Type: text/html

<h1>Hello, world!</h1>
```

### HTTP methods

<span id="post-put-and-patch"></span>

| Method | Typical use |
| --- | --- |
| GET | Retrieve a representation |
| POST | Ask a resource to process a representation, often to create something |
| PUT | Create or replace the state at a known resource URI |
| PATCH | Apply changes described by the request body |
| DELETE | Remove the target resource's association with its URI |

GET, PUT, and DELETE are idempotent in HTTP semantics. Repetition can still produce different status codes. A PATCH operation can be designed to be idempotent, depending on the patch format and operation. [HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2), [PATCH Method for HTTP](https://www.rfc-editor.org/rfc/rfc5789.html#section-2).

### HTTP status code

1xx is informational, 2xx indicates success, 3xx handles redirection or cache validation, 4xx signals a client-side error, and 5xx signals a server-side error.
